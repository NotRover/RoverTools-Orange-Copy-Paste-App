The change, in one gesture

Sharing into a space you cannot read yet

This is the whole thing. Before, that gesture had nowhere to go: the row was greyed out and the command refused. Now the intent is recorded, the entry is held, and it goes out by itself when the key lands.

Was · dead end

Two states with no edge between them. The only way out was to come back later and share again by hand — if you remembered.

Now · one path through

The queue is the share record already on disk (id_map.json), so a restart changes nothing. The push path still drops a keyless space, so nothing unreadable ever reaches the server.

The mechanism underneath

Where a key can come from

The blocked state did not need better copy, it needed to become rare. A Space Key had exactly one source; it now has three, and two of them do not need anybody to be at their desk.

Surface by surface

What a person actually sees

Ten places changed. The rule behind all of them: a queued share must never look like a delivered one, nothing on screen should be dead, and anything that happens while you are away should still be there when you get back.

Was Always the owner's app, because it was the only thing that could help.

Was Nothing. The only sign was the waiting notice quietly disappearing, which you saw only if you happened to be on that screen.

Same two minutes, both ways

Joining, then trying to share

Read the two together. The before diagram has two failure shapes in it: the member is stuck, and the only actor who can unstick them is one specific person's running process.

Deliberately unchanged

What this does not fix

Notifications are in-app, not desktop

All three new rows go to the notification centre, which is durable and survives a restart. None of them raise an OS-level notification — that is a separate decision and the app does not do it for anything yet.

A comment notification carries no text

It says who and where, which is enough to make you open the thread. The decrypted body is deliberately left out: the notification store outlives the entry it points at, and space content should not.

The feed is still empty while you wait

Content is encrypted under the Space Key, so there is genuinely nothing to render. No amount of UI makes that readable, and pretending otherwise would be the worse failure.

A leaked space code still admits a stranger

One multi-use code per space, valid 72 hours. Per-invite tokens and single-use codes were considered and dropped: they close a real hole at the cost of a second code format, a second link shape, and expiry copy.

A bad key is refused, not retried

A correctly wrapped wrong key unwraps fine and then decrypts nothing. Waiting cannot turn it into the right one, so the app says so instead of spinning. The owner removing whoever sent it rekeys the space.

Still passive-server end-to-end

A wrap is opened against a public key the server returned, unpinned. The fingerprint check defends against another member, not against the server that also serves the fingerprint.

Where it stands

Verified, and not

Worth being blunt: none of the flows above have run against a live backend. Migration 0017 is unapplied, so the queued-share flush, the invite pre-wrap, and the fingerprint refusal are confirmed only by compilation and by reading.
